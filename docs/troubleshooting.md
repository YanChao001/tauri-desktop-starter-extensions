# 市场排障手册

先区分客户端读取、包安装、本地构建和远端发布的失败，再处理对应边界。记录宿主版本、市场提交或 Release 标签、目录修订、插件 ID / 版本和稳定错误码；不要上传用户数据、密钥或完整会话。发布流程见 [发布与维护](./publishing.md)，权限和报告渠道见 [安全规范](./security.md)。

## 客户端错误

| 错误码                   | 典型原因                                                                    | 处理方法                                                                                   |
| ------------------------ | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `MARKET_NOT_CONFIGURED`  | 宿主没有有效仓库或受信公钥                                                  | 由应用维护者核对宿主市场配置，与 `public-key.txt` 和目标仓库一致后重新构建；不填写随机公钥 |
| `MARKET_INCOMPATIBLE`    | 已验签的目录使用不支持的 schema                                             | 核对配套宿主和真实 latest 目录，重新构建并发布当前协议；签名有效并不表示协议兼容           |
| `MARKET_EXPIRED`         | 当前协议的已签名目录到期                                                    | 校准设备时钟；若确实到期，由维护者以更高 revision 续签并发布，刷新后重试                   |
| `MARKET_INVALID`         | 签名、目录结构、时间范围、包大小或哈希不一致，或目录回退 / 同号替换         | 保留错误与目录证据，核对信任公钥、附件、发布修订和时钟，不跳过校验                         |
| `MARKET_UNAVAILABLE`     | 网络、HTTPS、GitHub 状态、下载超时、缺少附件或本地信任记录的 I/O 失败       | 确认 Release 已公开、附件完整、网络和应用数据目录可用，再刷新；此错误可重试                |
| `MARKET_CHANGED`         | 页面所选包或来源收据已经与当前目录不同                                      | 刷新市场，重新审阅并选择当前包；不要重用之前下载的来源收据                                 |
| `EXTENSION_INCOMPATIBLE` | 扩展包/API 或 `minHostVersion` 不适合当前宿主，或客户端扩展注册表版本不兼容 | 区分具体发生阶段；更新配套包或宿主。旧开发版注册表按宿主扩展指南的应用内归档流程处理       |

错误码由原生边界返回。旧客户端可能将不兼容或过期显示为统一的“市场目录或扩展包校验失败”；先确认运行的原生程序确实包含最新诊断，刷新前端页面不能替换仍在运行的 Rust 进程。

### 已验签但仍然不兼容

当前协议使用目录 schema 2、包格式 3 / API 2、视图版本 2。旧 schema 1 目录即使公钥正确且签名有效，仍会被新宿主拒绝。维护者需要从配套源码重新构建所有包、生成 schema 2 目录并生产签名发布，不能只改客户端提示、修改 JSON 版本号或允许旧 DTO 进入执行边界。

反过来，新目录也不保证老宿主能够理解；清单 `minHostVersion` 只是包的最低版本声明，不能给旧宿主补上新协议实现。跨仓库更新顺序见 [固定配套宿主](./publishing.md#固定配套宿主)。

### 已推送分支但市场仍是旧内容

客户端只读取配置仓库的公开 latest Release。核对 `main` 是否已经合并、发布工作流是否成功、草稿是否公开并标为 latest，以及 `catalog.json` 和全部包是否已上传。更新本地子模块、推送功能分支、创建 PR、通过离线验签都不会更新该地址。

可先用以下只读命令检查远端状态，仓库名按 [listings.json](../listings.json) 的实际值替换：

```sh
gh release view --repo YanChao001/tauri-desktop-starter-extensions --json tagName,isDraft,isPrerelease,targetCommitish,publishedAt,assets
gh workflow list --repo YanChao001/tauri-desktop-starter-extensions
```

不要把某次排障时观察到的线上标签写成永久规则；每次都核对实际 Release。客户端普通读取有短期缓存，显式刷新可重新获取；下载前也会重新检查当前目录。网络失败时展示的旧已验证内容，不意味着当前下载与安装一定可用，过期目录不会继续获得安装资格。

### 签名有效但包校验失败

目录同时记录完整 JSON 包的 `packageSha256` / `packageBytes` 与内含 Wasm 的哈希和大小；任意一层不符都会拒绝安装。常见原因是签名后重新打包、格式化 JSON、上传了同名旧附件，或清单与编译产物不同。

先对完整发布目录运行 `node scripts/verify.mjs <目录>`，核对所有包而非只核对 Wasm。失败时从已审核源码重新构建并发布更高修订号，保留原目录供比较。不要在客户端重新计算一个“期望哈希”来接受变化，也不要覆盖已公开同修订目录。

### 时间、过期与目录回退

确认设备 UTC 时间和时区设置正确。时区只影响显示；签名使用 Unix 秒。`expiresAt` 已到期报告 `MARKET_EXPIRED`，签发时间过远、期限颠倒或超过允许窗口属于 `MARKET_INVALID`。

同一仓库和公钥的客户端会跨重启保留最高修订号及 payload 摘要。将旧 Release 设为 latest、重新签署同修订目录、仅修改有效期或推荐标记，均可能触发拒绝。修复是发布更高修订号的完整目录，不删除信任状态、不倒拨时钟、不关闭验签。

## 本地构建与真实 Wasm 校验

### 找不到 `extension-tool`

`STARTER_EXTENSION_TOOL` 必须是现有 `extension-tool` / `extension-tool.exe` 的绝对路径，不能指向桌面主程序、脚本或任意重命名工具。子模块布局可自动探测宿主的 debug 路径；独立市场检出必须显式指定。按 [开发指南](./development.md) 先准备平台依赖、构建宿主前端资源，再构建 CLI。

切换宿主源码后重新构建 CLI，不能只将环境变量指向旧二进制。如果 `expectJsonSubset`、清单字段或输出格式被报告未知，先核对工具对应的宿主提交是否具备该协议和 fixture 功能，避免删除断言来让旧工具通过。

### Rust 目标或插件产物缺失

使用 [rust-toolchain.toml](../rust-toolchain.toml) 指定的工具链，并为该工具链安装 `wasm32-unknown-unknown`。在市场仓库执行 `rustup target add wasm32-unknown-unknown`；如环境显式设置 `RUSTUP_TOOLCHAIN`，确认没有选到另一工具链。`build.json` 中的 `.wasm` 文件名须与该插件 Cargo 库名对应，构建脚本从各插件独立的 target 目录取产物。

锁文件、格式或源代码错误应直接修复，再运行 `check.mjs`。不要移除 `--locked`、删除所有锁文件或手工复制旧 Wasm 规避失败。ABI、资源或视图校验错误需要按宿主返回的阶段和消息修复，不改为跳过真实运行。

### 已存在相同修订目录

`Release directory already exists` 表示 `dist/market-<revision>` 已存在，脚本不会覆盖。先保留并核对旧产物，再选择新的本地检查修订号。正式发布修订还必须高于已有非草稿 Release 和已被客户端接受的最高修订号；仅换目录名不能改变已签名 payload 的 revision。

## CI 与生产发布

### PR CI 使用了旧宿主或无法检出 ref

PR / main CI 使用 `STARTER_HOST_REF` 仓库变量，默认是 `develop`；发布工作流的 `host_ref` 输入不会影响 PR。查看 Actions 摘要记录的实际宿主 SHA。协议修改尚未进入默认分支时，先推送并审核所需宿主提交，配置该变量后重跑 CI。

本地未推送的 SHA、拼错的分支、不可读仓库或已移除的 ref 都会导致检出失败。修正远端可读的固定提交及权限，不能用本机产物替代 CI 的源码来源。独立 CI 会安装宿主 Linux 依赖并准备前端构建；某平台通过不能替代其他目标系统的运行验收。

### 生产 Secret 缺失或与公钥不匹配

`Signing key does not match public-key.txt` 表示没有提供私钥，或提供的有效私钥与受审阅公钥不是一对。若传入的 PEM 内容不完整或格式无效，Node 密钥解析会直接报错，不一定出现该错配消息；`MARKET_KEY_FILE` 路径不存在或不可读也会直接报告文件错误。本地签名可通过该变量读取仓库外 PKCS#8 PEM 私钥文件。按具体错误分别检查 Secret 是否配置、文件是否可读、PEM 格式和公钥对应关系，不将值打印到日志、issue、命令行或聊天。

普通 PR / `check.mjs` 不需要该 Secret，其成功不能证明生产签名配置可用。不要为通过发布而随意替换公钥；真正轮换需同步宿主信任配置和升级计划，见 [公钥轮换](./publishing.md#下架回退与公钥轮换)。

### revision 重复或发布目标 SHA 错误

`Market revision must increase` 表示新修订没有高于脚本读取的最近 100 个非草稿 Release 中的 `market-*` 修订。选取更高修订，从构建开始重新执行；维护要求是全历史递增，客户端还可能见过列表之外或现已删除的更高修订，维护者需要结合发布记录判断。

`Release source must be a complete 40-character commit SHA` 表示发布没有可靠的源码身份。Actions 使用市场仓库的 `GITHUB_SHA`；本地必须提供 `MARKET_SOURCE_SHA`。若两个变量同时存在，前者优先。核对 SHA 已在远端存在，并对应包的已审核市场源码，不使用宿主 SHA、短 SHA 或可变分支名。

### 上传失败或只看到草稿

脚本先创建 draft，再上传全部附件，最后才公开并设置 latest。网络、附件冲突或权限失败时草稿可能仍在。检查运行日志、草稿及完整附件，按 [发布流程](./publishing.md#actions-生产发布) 处理，不能手动公开不完整草稿来消除错误。

如果包已公开后发现问题，用更高修订目录下架或修复。不要覆盖公开附件、降低修订或宣称删除 Release 会卸载用户已安装插件。

## 数据保留与求助

市场读取或下载失败不需要删除扩展注册表、私有存储、系统凭据或信任记录。旧开发版扩展注册表使用宿主提供的确认归档流程；损坏、未来版本和未知数据保留原件，不能假定为可重建旧版本。不要在应用仍使用目录时从外部搬动它。

普通 bug 报告提供错误码、版本、提交 / Release、复现步骤和脱敏日志。涉及签名绕过、恶意包或密钥泄露时，按 [安全规范](./security.md#漏洞与密钥事件) 私密报告。记录已完成的检查与未验证范围，不把浏览器 mock、离线 fixture、CI 配置或本地签名当成真实桌面及线上发布成功。
