# 市场发布与维护

本文定义从已审核源码到客户端市场的分发流程。开发和离线验收见 [开发指南](./development.md) 与 [测试规范](./testing.md)，信任边界见 [安全规范](./security.md)。命令默认在市场仓库根目录执行；使用宿主子模块时，对应 `marketplace/`。

## 发布的五个阶段

| 阶段                              | 产生的结果                               | 是否更新客户端市场 |
| --------------------------------- | ---------------------------------------- | ------------------ |
| 本地提交                          | 可审阅的源码和提交 SHA                   | 否                 |
| 推送分支、创建 PR                 | 远端可检出的代码与检查结果               | 否                 |
| 审核合并 `main`                   | 已批准的发布来源，命中范围时自动触发发布 | 待后续阶段成功     |
| 构建、离线验收                    | 全部包与未签名目录，临时密钥验证结果     | 否                 |
| 生产签名、完整上传并发布为 latest | 受信任 `catalog.json` 和对应包的 Release | 是                 |

宿主读取配置仓库的 `releases/latest/download/catalog.json`，不会读取本地子模块、功能分支或 PR。仅推送分支、通过 CI、更新宿主子模块引用，均不能使新插件出现在市场。线上是否生效应核对实际 latest Release、目录签名、修订号和附件，不能从源码状态推断。

## 固定配套宿主

市场工具调用宿主的 `extension-tool`，由相同的 Rust 规则检查清单、Wasm ABI、命令输出和视图。当前目录为 schema 2，扩展包为格式 3 / API 2，视图为版本 2；各包还声明 `minHostVersion`。旧目录不能仅修改版本数字后继续使用，必须从配套源码重新构建并签名。

当前四款插件最低要求均为 **0.1.7**，精确版本以各自 `extension.json` 为准。开发阶段只验证选定的当前宿主或固定的待发布提交，不承诺历史版本兼容，也不维护旧正式版本矩阵。源码与本地包不代表线上 latest 或宿主安装包已更新，发布前核对实际 Release。

当前内网通信插件提供流式文件传输、图片与真实本机回环，插件版本以其[清单](../plugins/lan-chat/extension.json)为准，须使用包含这些服务实现的配套宿主源码重新构建。当前沿用 `0.1.7` 开发基线，旧同版本快照不具备新能力；版本号相同不能代替固定宿主 SHA 和真实服务验证。正式分发仍须提升包含新能力的宿主发布版本并同步准确最低版本，不能以现有开发清单声称已兼容线上包。

本轮内网通信使用 LAN wire 协议 **v2**，握手明确拒绝 **v1**，不能与旧协议端点互通。通信双方须先升级并重启包含 v2 实现的配套 **0.1.7 宿主**，再安装本轮插件；只升级一端或插件不能完成协议升级。`minHostVersion` 只声明最低版本门槛，不能代替同版本快照的实现核对；发布前须确认两端安装包来自包含该能力的已审核宿主提交。协议与数据边界以[宿主 LAN 说明](https://github.com/YanChao001/tauri-desktop-starter/blob/develop/docs/extensions.md#局域网通信)为准，不通过降低握手版本或删除历史数据恢复连接。

0.1.6 起可隔离已验签 schema 2 目录中的未来条目，保留只读展示但拒绝下载；严格条件与完整信任检查见 [兼容与演进](./architecture.md#兼容与演进)。

0.1.5 及更旧二进制没有这项修复：未知权限 / 图标可能在 `minHostVersion` 检查前就引发 `MARKET_INVALID`。更新并重启原生宿主，不能通过换公钥、跳过验签或刷新前端补上实现。

正式发布时必须提高包含新能力的宿主版本，并让插件声明准确的 `minHostVersion`；开发快照即使版本相同，也不保证实现相同。未知、未来或损坏的存档继续保留原件并拒写，不因开发协议变化引入未经实现的迁移，也不能通过删除用户数据修复网络接口变化。

独立 CI 的宿主来自 [.github/actions/host-tool/action.yml](../.github/actions/host-tool/action.yml)，与本机子模块旁的宿主代码无关：

- [PR / main 检查](../.github/workflows/ci.yml) 使用仓库变量 `STARTER_HOST_REF`，未设置时使用 `develop`。
- [发布工作流](../.github/workflows/publish.yml) 自动触发时使用 `STARTER_HOST_REF`，手动触发时可用本次 `host_ref` 输入覆盖；必须为已推送并审核的完整 40 位提交 SHA。未配置、分支名和标签均在构建前拒绝，没有可变分支回退。
- `host_ref` 只覆盖这一次发布，不会修复 PR CI 的默认宿主选择。

跨仓库修改先推送并审核宿主提交，再将 `STARTER_HOST_REF` 固定为其完整 SHA，重跑市场 PR 检查后合并发布。未推送的 SHA 无法检出，本地修改不会更新远端变量；评审核对 Actions 摘要中的实际宿主提交。

修改最低版本会改变包内容，已有分发版本必须提升插件版本并同步 Cargo 清单与锁文件，不能以同版本替换已签字节。选定当前宿主的真实 Wasm、包完整性与现有主仓 SDK 集成检查分别按 [测试规范](./testing.md) 执行。

## 发布前验收

维护者应检查所有收录插件的源码、许可证、依赖、清单权限和实际行为，而非只检查新增项。当前收录清单由 [listings.json](../listings.json) 定义；新增或删除项目后，发布的是新的完整目录。

1. 通过 PR 审核源码和锁文件，确保每条命令都有手写 fixture，覆盖离线使用、可选授权、错误恢复及效果回执。
2. 用配套宿主构建 `extension-tool`，按 [测试规范](./testing.md) 完成业务规则、真实 Wasm、宿主安装和交互验收。离线 fixture 的合成存储响应不能替代真实存储验收。
3. 从已审核的 `main` 提交执行全部插件检查，保存 Actions 使用的市场 SHA、宿主 SHA 和结果。真实桌面、目标系统或系统凭据未验收时，在 PR / Release 中说明。
4. 确认生产公钥 [public-key.txt](../public-key.txt) 与目标宿主配置相符，且生产私钥只存在于受控 Secret 或仓库外的受保护文件。
5. 选择严格递增的目录修订号，检查完整包、模块和 UI 文档哈希，确认拟发布标签未被其他提交占用，再执行下面的生产流程。

HTML、权限或服务联动须核对宿主包含对应实现与生命周期修复，市场清单接受新字符串不代表客户端已具备能力。开发快照可能共享版本号，仍以固定 SHA 为验收证据；插件解析、真实 Wasm、宿主服务与真实环境按 [测试规范](./testing.md) 分别记录。

涉及本轮内网通信时，发布 PR 与 Release 须明确记录 v2 拒绝 v1、双方配套升级 0.1.7 的操作及实际两端验证范围。离线 fixture 或单机回环不代表跨设备通信已验收；未完成时如实说明，并保留现有联系人、历史与原始存档。

## Actions 生产发布

插件、`listings.json`、市场脚本、工具链、公钥、相关 Actions 或发布工作流发生变化并经 PR 合入 `main` 后，“发布市场”自动执行完整构建、生产签名、附件上传与公开 latest；纯 Markdown 文档改动不触发。精确路径范围以 [publish.yml](../.github/workflows/publish.yml) 为准。构建与签名失败时不会公开本次目录，合并或运行开始都不能代替发布成功证据。

工作流仅允许 `main` 执行构建 job，也保留 `workflow_dispatch` 用于手动发布和目录续签。自动触发及手动 `revision` 留空时使用当前 Unix 秒；手动也可指定十进制正 `u32`，前导零会规范为十进制整数，科学计数法、十六进制和带空白的输入会拒绝。修订号不等于插件版本：续签、下架和推荐调整也需要新的修订号，插件语义版本只在插件内容变化时按实际变更调整。

工作流分为两个独立 job：

| Job       | 处理内容                                                                                                      | 生产签名权限                                                       |
| --------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `build`   | 脚本与界面回归、全部插件原生单测和 Clippy、构建宿主工具、真实 Wasm fixtures、一次性密钥验签、上传本次修订产物 | 不注入生产私钥，仅仓库读取权限                                     |
| `publish` | 下载上一 job 产物，重新对照已审核清单、完整包哈希签名并验签，上传和发布                                       | `MARKET_SIGNING_PRIVATE_KEY` Secret 与发布所需的 `contents: write` |

生产签名 job 等待构建成功，不执行插件编译；签名前核对清单、Wasm、UI、规范包字节与目录预览，收录信息及 HTML 摘要必须匹配审核过的 checkout。`catalog.json` 不覆盖创建，已签名目录不能原地重签；密钥隔离见 [安全规范](./security.md#密钥与构建隔离)。

发布脚本独立验证签名目录与全部附件，将核验的确切字节写入本次新建的系统临时目录，后续只上传该快照，并在结束时清理。原产物在核验后被替换不会改变上传内容。脚本分页读取完整 Release 历史，要求修订号高于所有非草稿 Release 的 `market-*` 修订；历史读取失败或响应结构异常时停止，不创建草稿。删除 Release 不能抹去客户端已接受的最高修订，维护者仍须结合发布记录保持修订递增。

来源检查通过后，脚本使用 `--target GITHUB_SHA` 指定草稿 Release 的源码提交，上传快照中的 `catalog.json` 与全部目录所列插件包，最后才将草稿公开并设为 latest。`GITHUB_SHA` 是市场源码提交，不能误填成宿主提交。

预先存在的同名标签不会因 `--target` 改指向。脚本在创建草稿前和公开 latest 前两次核对精确标签：不存在时继续，存在时须解引用到相同源码 commit。带注释标签最多解引用 8 层，循环、异常、错配或 API 失败均拒绝；前缀匹配不能当作精确标签，网络 / 权限错误不能当作不存在。初次失败不创建 Release，上传后失败保留草稿。实现见 [publish.mjs](../scripts/publish.mjs)。

仓库和标签写权限仍须由受控维护者持有；这些检查不能代替保护规则，也不能保证其他授权者不会在检查之后修改远端标签。

上传失败会留下草稿，不会主动将其设为 latest，也不会自动删除已有 Release。先检查草稿附件与执行日志，确认没有公开半成品，再由维护者处理草稿并重试。脚本不覆盖同标签附件，也不自动恢复已存在的草稿；不能把失败日志或草稿链接当作发布成功证据。

### Release 说明格式

每次发布自动生成固定章节：发布信息、破坏性变更、更新内容、插件版本、使用与验证、完整变更。信息取自本次已验签目录，列出修订号、签名有效期、插件版本和各自最低宿主版本；提交与完整对比链接指向本次确切市场源码 SHA。

变更基线为最高修订号的已公开、非预发布 `market-*` Release，读取其标签所指提交至本次源码 SHA 的 Git 历史；首次正式发布读取全部历史。合并提交不重复列入，其底层普通提交仍参与分类。按照 Conventional Commits 自动提取 `feat`、`fix`、`perf`、`refactor`、`docs`、`build`、`ci`、`test`、`style`、`chore`、`revert`，未识别的提交保留在“其他变更”。`!`、`BREAKING CHANGE:` 和 `BREAKING-CHANGE:` 会额外进入破坏性变更章节，详细升级步骤应写入对应提交正文。续签或只有合并提交时明确说明没有新增非合并提交，源码差异仍可通过完整对比核对。

GitHub 自带的[自动发行说明](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes)按 PR 标签分类；本仓库直接读取提交类型，不要求维护者重复设置 PR 标签。发布 job 检出完整 Git 历史与标签，本地发布也须保留完整历史和已有正式标签；缺失标签、历史断裂或说明超过大小上限时，在创建 Release 前停止，不静默生成不完整的变更列表。说明通过临时 UTF-8 文件交给 `gh release create --notes-file`，随后清理。

发布说明只报告可从提交与签名目录核实的事实，不自动声称真实桌面、多机网络和全部平台已验收。维护者仍须在 PR 中记录实际检查范围和升级影响，并在公开前审阅破坏性变更与最低宿主要求。

## 本地受控发布

正常开发仅运行 `check.mjs`，无需生产密钥。维护者在确需本地发布时，使用已审核并推送的完整市场提交、仓库外私钥文件和具有目标仓库发布权限的 `gh` 会话。以下是 PowerShell 示例，路径和修订号须替换为真实值：

```powershell
$env:STARTER_EXTENSION_TOOL = "E:\tools\extension-tool.exe"
$env:MARKET_REVISION = "<高于已发布目录的正整数>"
$env:MARKET_SOURCE_SHA = (git rev-parse HEAD).Trim()
node scripts/build.mjs
$env:MARKET_KEY_FILE = "E:\protected-market-keys\release.pem"
node scripts/sign-release.mjs "artifacts/market-$env:MARKET_REVISION"
node scripts/verify.mjs "artifacts/market-$env:MARKET_REVISION"
node scripts/publish.mjs "artifacts/market-$env:MARKET_REVISION"
```

每步成功后再执行下一步。`STARTER_EXTENSION_TOOL` 必须是宿主工具的绝对路径；本地发布缺少 `MARKET_SOURCE_SHA` 或其不是完整 40 位 SHA 时会拒绝。若环境中已有 `GITHUB_SHA`，它优先于 `MARKET_SOURCE_SHA`，执行前应检查这两个变量，确保标签指向本次包的已审核源码，而不是残留 CI 提交。

生成目录不覆盖已有 `artifacts/market-<revision>`；发布时使用本次新目录，保留上一已发布目录作核对。私钥不得放入仓库、构建产物、日志或命令行字面量，使用结束后清除当前会话中不再需要的密钥路径和发布环境变量。

## 有效期与续签

签名时以当前 UTC Unix 秒重写 `issuedAt` / `expiresAt`，默认有效期为 7 天。宿主拒绝超过 30 天的签名窗口、超过当前时间 5 分钟的未来签发时间，以及已经到期的目录。具体定义见 [protocol.mjs](../scripts/protocol.mjs) 与配套宿主实现。

维护者需要在到期前安排续签：即使插件未变化，也以**更高修订号**重新构建、验收、签名和发布完整目录，可在 `main` 手动运行 `workflow_dispatch`。相关源码变更合入后会自动发布，但没有定时续签任务；采用此有效期时仍应安排维护人员和提醒。不能只延长已发布附件的日期、用原修订号重新签名，或让客户端忽略过期检查。

宿主按“仓库 + 原始公钥指纹”记录最高修订号和 payload 摘要。相同修订号只能对应完全相同的已签名 payload；更低修订号和同号替换都会被拒绝。短期缓存不延长签名有效期，过期目录不能用于下载或安装。

## 下架、回退与公钥轮换

- **下架**：从 `listings.json` 移除项目，发布更高修订号的完整目录。客户端刷新后不再提供新下载；已安装插件和用户数据保留，没有远程卸载机制。仅删除 Release 或包附件可能造成下载失败，不能代替下架目录。
- **修复或回退分发内容**：使用更高目录修订号重新发布经过审核的包，说明用户操作和数据影响。不要把旧 Release 重新设为 latest 来降低目录修订号。宿主的“回退上一安装包”是用户显式的本地操作，与目录防回退分别执行；市场发布不会自动降级用户现有安装。
- **公钥轮换**：在受控位置生成新密钥，将新公钥提交到 `public-key.txt` 并同步宿主受信配置，经审阅和配套发布后才切换签名 Secret。当前单公钥配置没有双签过渡；旧宿主不信任新钥，新宿主也不接受旧钥签名目录，必须明确支持窗口与升级要求。

仓库或公钥改变会形成新的信任范围，但不能作为降低修订号或绕过完整性检查的恢复办法。轮换时仍保持发布修订递增，保留来源和发布记录；怀疑密钥泄露时按 [安全规范](./security.md#漏洞与密钥事件) 处理。

## 发布后核对

核对实际公开的 latest 标签、target commit、签名目录、有效期和全部附件；再由受信宿主刷新目录，检查下载、权限确认和安装后运行。验证时使用隔离数据和测试设备，不覆盖真实用户存档。若仅完成 CI、离线验签或本地安装，应明确记录这些范围，不能写成已完成线上发布或所有目标平台验收。
